Local dev environments that already look like production.

gosite scaffolds a Go monolith — Echo v5, html/template, htmx, Alpine — with Cockpit CMS and a Redis page cache. It serves every project at https://name.test with a trusted certificate, hot-reloads on save, and emits the compose file Coolify deploys from.

The problem

Every local stack drifts away from production.

Different ports, no TLS, a CMS wired by hand, a cache that only exists on the server. gosite closes that gap by giving development the same shape as the deploy: one shared proxy, one network, one compose format.

One command, one site

gosite create writes the Go app, the Cockpit container, both compose files, the Dockerfiles, hot reload config and its TLS certificate. Nothing to wire by hand.

Cached by default

The rendered page lives in Redis behind a cache-aside helper. A hit skips the CMS call and the template render entirely, and concurrent misses collapse into a single render.

Real HTTPS, locally

Traefik plus mkcert serve name.test and cms.name.test with a certificate your system trusts. Green padlock, no warnings, no /etc/hosts edits.

Caching

The CMS stays off the request path.

The fully rendered page is cached, not the data — so a hit costs a Redis read and nothing else. The parts that usually go wrong are handled for you.

One helper, not a pattern

Cache.HTML(key, render) is the whole API. Caching another page is a call, not another copy of the same Get/Set dance. A Redis outage degrades to a slow page, never an error.

No thundering herd

Concurrent misses of the same key are coalesced with single-flight: one render runs, the rest wait and share it. Measured cold, 60 requests at 30 concurrent produced exactly one call to Cockpit.

Warm again immediately

Purging re-renders in the background before it answers, so the next visitor after an editor publishes never pays the cold path. In development a floating button does it; in production it is a webhook.

Command surface

Small enough to remember.

Every project command takes an optional name — omit it inside the project directory, pass it to act on any project from anywhere.

Cockpit addons

Addon modules, shipped with gosite.

Addons are plain folders at /var/www/html/addons — bind-mounted in dev, baked into the production image by Dockerfile.cms — so nothing loads unless it exists. Every project ships four built-ins; Forms and Replica are opt-in at setup (--addons "Forms Replica", or --no-addons to skip). Refresh or add them later with gosite sync --addons.

AssetsUpload built-in

A public POST /api/assets/upload endpoint for dropping files straight into Cockpit's asset library, with optional folder targeting — no admin UI required.

ModelManager built-in

REST CRUD for content models: list, save (create or update) and remove via /models, with ACL-aware filtering so each role only sees what it may edit.

CloudStorage built-in

S3-compatible uploads for the core CMS: MinIO in dev, AWS / R2 / Backblaze in prod. Uses the Flysystem adapter the image already ships — no Pro license, no composer step.

AssetPathFix built-in

Strips the leading slash from uploaded asset paths so S3 public URLs don't get a double-slash (//) that breaks admin previews.

Forms optional

An inbox-style manager for website submissions: a public POST /forms/api/submit receiver with honeypot and rate-limit anti-spam, an admin screen per form, CSV export and mail/webhook notifications. The receiver is closed by default — list your site's origins in allowed_origins, and keep trustedProxies at 1 so the rate limit counts each visitor separately rather than the proxy.

Replica optional

Content replication between Cockpit instances: push/pull, multiple targets, mirror/merge conflict handling, dry runs, a CLI and an activity log — no commercial addon required.

What gets generated

A layout you can read in one sitting.

One file per responsibility, read top to bottom. Dependencies point one way, so markup changes cannot break the cache and vice versa. 

cmd/server/        entry point (main, app, router)
internal/           application packages
  app/             App struct, NewApp, NewRouter
  config/          env, read exactly once
  handlers/        one file per route
    handlers.go    shared dependencies
    response.go    how the app replies
    home.go        GET /
    purge.go       POST /cache/purge
    health.go      GET /healthz
  cache/           cache-aside over Redis
  cms/             the Cockpit API client
  views/           embedded with go:embed
    render.go      parsed once at startup
    layout.html
    pages/         one file per page
    components/    one file per piece
cockpit/            CMS config + addons
deploy/             Dockerfiles
MEMORY.md          AI entry point
ARCHITECTURE.md    the reference it points at
  • Echo v5. Handlers take *echo.Context, Start owns graceful shutdown, and every route is registered in router.go — nowhere else.
  • No build step. html/template with go:embed, htmx and Alpine from a CDN. No bundler, no node_modules, no generated code.
  • One cache helper. Cache.HTML(key, render) — caching another page is a call, not another copy of the same Get/Set dance, and concurrent cold renders are coalesced.
  • Cockpit, not coupled. One package talks to the CMS. When it is unreachable the template falls back to its own copy, so a fresh project renders on the first run.
  • Dev tooling stays in dev. The cache-purge button renders only when APP_ENV is a development value, and carries its own scoped CSS — production ships neither.
  • Written for assistants too. MEMORY.md and ARCHITECTURE.md ship with real values filled in — module path, domains, cache key.

Local domains

Every project on its own hostname, over TLS.

A dnsmasq wildcard points *.test at localhost, mkcert issues a certificate covering the site and its CMS subdomain, and a shared Traefik routes by container label — the same mechanism Coolify uses in production.

Wildcard DNS

One address=/.test/127.0.0.1 line and a new site works the moment it starts — no host file edits, ever.

Trusted certificates

Each project gets a certificate for name.test and *.name.test — a wildcard matches one label, so the CMS host needs its own.

Shared infrastructure

Redis runs once per machine on gosite-network. MongoDB runs once per machine too — gosite-mongo — so each project shares the same database server, just like production.

Hot reload

air watches every package and template. A change to a single component is live in about three seconds — no restart.

Asset storage

Files in a bucket, not on disk.

Every project can keep its asset uploads in an S3-compatible bucket. Local development uses a shared MinIO service in the infrastructure; production targets any S3-compatible provider. The default is local — flip STORAGE_ADAPTER=s3 in .env (or the Coolify dashboard) to switch — so nothing changes unless you ask for a bucket.

MinIO locally

The shared infrastructure runs a gosite-minio container with native TLS: gosite infra up issues an mkcert certificate and mounts it, and Traefik exposes the S3 API at https://minio.test and the console at https://minio-console.test (plain-HTTP fallbacks on 9002/9003). Set S3_VERIFY=false and S3_PUBLIC_URL=https://minio.test/assets so assets and thumbnails load straight from the bucket.

S3-compatible in prod

Point the same variables at AWS S3, Backblaze B2 or any S3 endpoint and the CMS stores assets there instead. Keys are mounted from the Coolify dashboard — never committed.

Backward compatible

STORAGE_ADAPTER defaults to local, so every existing project keeps working untouched. Enable the bucket per environment by editing one variable — no code or image changes required.

Updating an existing deployment: /cache/purge used to treat a missing COCKPIT_API_TOKEN as “no authentication required”, which left the endpoint public on any site that forgot the variable. It now fails closed — set the token in the Coolify UI before you redeploy, or purging stops working. Run gosite doctor first: it reports every project missing the token, along with the rest of the secure defaults, without changing anything.
